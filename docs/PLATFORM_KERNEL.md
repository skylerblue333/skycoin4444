# SKYCOIN4444 Platform Kernel

## Purpose

The platform kernel is a small, deterministic control-plane library for reasoning about the integration state of the large SKYCOIN4444 codebase. It does not turn planned or mocked features into production capabilities. Instead, it makes dependencies, degradation, and runtime boundaries explicit and machine-readable.

## Capability graph

The kernel compiles capability definitions into a directed acyclic graph and rejects:

- duplicate capability identifiers;
- duplicate dependency declarations;
- missing dependency targets;
- cyclic dependency graphs;
- malformed stable identifiers.

Each graph receives a SHA-256 fingerprint over its normalized definitions. Reordering equivalent definitions does not change the fingerprint, so the value can be used as a stable engineering manifest identifier.

Dependencies are typed as either hard or soft:

- a hard dependency in an unavailable, disabled, unknown, or blocked state blocks its dependent capability;
- a degraded hard dependency degrades the dependent capability;
- a non-available soft dependency degrades rather than blocks the dependent capability.

The current server adapter derives observations from the canonical area registry. These observations describe source/integration maturity only. They are not proof of live providers, production deployment, security certification, financial settlement, blockchain execution, or regulatory approval.

## Runtime API

The server exposes:

- GET /api/platform/kernel
- GET /api/platform/kernel/capabilities/:id

Responses carry the request correlation id when available and explicitly keep productionReady set to false. The API is intended for engineering diagnostics, release tooling, and future Mission Control visualization.

## Request correlation

server/_core/requestContext.ts uses Node AsyncLocalStorage so the request id generated by the observability middleware follows asynchronous work without adding request-id parameters to every function signature. The tRPC context also exposes requestId.

This provides a foundation for structured logs, traces, audit envelopes, and provider adapters while preserving the existing X-Request-ID response contract.

## Resilience primitives

packages/platform-kernel/src/index.ts also contains reusable deterministic resilience primitives:

- bounded exponential backoff with optional jitter;
- injectable sleep/random functions for deterministic tests;
- configurable retryability decisions;
- a circuit breaker with closed, open, and half-open states;
- a single half-open probe guard to prevent a recovery stampede.

These primitives are libraries, not evidence that every external integration already uses them. Provider adapters should adopt them only where retry semantics are safe and idempotency has been designed explicitly.

## Verification

The root Vitest configuration includes the platform-kernel tests. Required root CI still performs type checking, package checking, lint, credential scanning, marker auditing, unit/integration tests, production build, and dependency audit.

The platform-kernel tests cover graph determinism, cycle rejection, hard/soft dependency semantics, retry behavior, circuit recovery, request-context propagation, and integration with the canonical area registry.
