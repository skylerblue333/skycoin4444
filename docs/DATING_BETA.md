# SKYCOIN4444 Dating Beta

## Purpose

SKYCOIN4444 Dating is an **18+ engineering-beta dating workflow**. The implemented path is:

**Dating home → profile → discovery → like/pass → mutual match → conversation → safety controls**

The current implementation is designed to prefer truthful state transitions over presentation-only success messages.

## Implemented server-backed capabilities

The authenticated `dating` tRPC namespace uses the existing dating tables in `drizzle/schema.ts` for:

- dating profiles;
- discovery preferences;
- likes and Super Likes;
- durable passes/rejected pairs;
- mutual matches;
- match-authorized messages;
- dating notifications;
- blocks;
- reports;
- subscription-tier read state.

### Profile

Authenticated users can persist:

- adult age;
- bio;
- general location text;
- up to eight bounded interests;
- gender;
- relationship intent.

The profile-setup page also keeps a browser-session draft so a user does not lose the full form when the server is unavailable. Fields that do not have a verified server/media contract in this flow—such as local photo file handles, display-name draft, height, body type, and verification preference—remain explicitly session-local.

### Discovery

Discovery:

- requires authentication;
- requires an adult dating profile;
- excludes the current account;
- excludes under-18 profiles;
- excludes private general profiles;
- excludes blocked relationships in either direction;
- excludes already-liked users;
- excludes active matches and rejected pairs;
- applies persisted adult age-range and gender preference;
- supports query-only general-location and interest filters;
- ranks by factual shared-signal count.

A shared signal is only:

- an exact normalized interest overlap; or
- an exact comma-delimited general-location component.

There is **no relationship-success prediction or compatibility percentage** generated by the new dating router.

Precise-distance filtering is intentionally unavailable because the beta does not collect or claim precise dating geolocation.

### Like, Super Like, pass, and match

A Like or Super Like is persisted only after the server accepts it. A mutual match is created only when reciprocal persisted interest exists.

A pass is represented as a rejected pair so the same profile is not repeatedly resurfaced in the current beta.

### Messaging

Messages are allowed only for an active mutual match where neither side has blocked the other.

The UI does not append an optimistic message before the mutation succeeds. Message text is bounded to the current database field limit.

Opening a conversation can mark incoming messages and related message notifications read.

### Unmatch, block, and report

- **Unmatch** closes the active match and removes conversation access.
- **Block** records the block, removes reciprocal dating likes, and closes the pair.
- **Report** records a pending report reason/details and can optionally block the profile.

A report being recorded does **not** mean an investigation, identity verification, moderation decision, law-enforcement report, or emergency response occurred.

### Notifications

Dating notifications are persisted for match/message/like events and can be marked read individually or in bulk.

## Safety center

`/dating-safety` includes:

- first-date safety checklist;
- session-local date-safety plan builder;
- local copy-to-clipboard plan text;
- a small deterministic warning-phrase helper for obvious categories such as money/crypto requests, credential/secret requests, gift cards, secrecy/isolation, and threats/pressure.

The warning helper is a reminder tool only. A phrase match is **not proof** that another person is fraudulent or dangerous, and the absence of a phrase match is **not a safety certification**.

The safety center does not monitor a date, share live location, notify a trusted contact, or contact emergency services.

## Premium / billing truth boundary

The dating subscription table can expose a stored tier, but the engineering beta does not currently claim:

- Stripe or other payment checkout for dating;
- subscription purchase;
- cancellation/refund handling;
- recurring billing;
- paid entitlement enforcement;
- paid boosts;
- paid visibility ranking;
- premium feature delivery.

The Premium page is therefore a product-direction surface, not a purchase flow.

## Explicitly not claimed

This implementation does **not** claim:

- government-ID verification;
- document-based age verification;
- background checks;
- criminal-record checks;
- precise or live dating geolocation;
- safety certification;
- relationship-outcome prediction;
- emergency monitoring or dispatch;
- production-scale abuse operations;
- paid dating checkout or billing;
- guaranteed message delivery outside the accepted beta API/database path.
